# Owndangan Development Roadmap — Implementation Prompt

Kamu adalah senior full-stack engineer yang melanjutkan development project **Owndangan**.

## Tujuan

Implementasikan roadmap development berikut secara bertahap dengan prinsip:

* Jangan merusak fitur existing.
* Jangan mengubah business logic yang sudah berjalan tanpa alasan kuat.
* Jangan membuat duplicate implementation.
* Reuse service, repository, component, API client, middleware, validation, dan utility yang sudah tersedia.
* Ikuti architecture dan coding convention project saat ini.
* Semua perubahan harus production-ready.
* Setiap feature harus memiliki test yang relevan.
* Jangan mengerjakan feature di luar scope yang sedang ditugaskan.
* Jangan menghapus atau mengubah test existing hanya agar test menjadi hijau.
* Jika menemukan pre-existing failure, dokumentasikan dan jangan menganggapnya sebagai regression.
* Jalankan formatter/linter/test setelah setiap tahap.
* Jangan menggunakan mock/fake implementation untuk feature yang seharusnya benar-benar bekerja.
* Jangan mengarang data, testimonial, user, transaction, atau API response.

# PHASE 3 — WhatsApp Integration

## Priority: 🔴 Market Fit

Mulai dari implementation yang aman dan provider-agnostic.

### WA Link Generator

Generate message:

```text
Halo {guest_name},

Kami mengundang Anda untuk hadir di acara pernikahan
{bride} & {groom}.

Silakan buka undangan:
{invitation_url}
```

Guest name harus dipersonalize.

Generate:

```text
wa.me/{phone}?text={encoded_message}
```

Pastikan URL encoding benar.

### RSVP Notification

Ketika RSVP berhasil:

```text
RSVP
 ↓
Notification
 ↓
WhatsApp / configured channel
```

Jangan mengirim pesan WhatsApp secara langsung dari request jika membutuhkan external API.

### WhatsApp Broadcast

Untuk Pro tier:

* Select guests
* Preview message
* Personalization
* Send
* Track status
* Handle failure
* Rate limit
* Retry safely

Jangan membuat bulk sender yang dapat menyebabkan spam tanpa rate limiting.

### Provider Integration

Buat abstraction agar provider dapat diganti:

```text
WhatsAppService
    ↓
Provider Interface
    ↓
Fonnte / Wablas / Twilio / WhatsApp Business API
```

Jangan hard-code provider di business logic.

# PHASE 6 — Performance & Caching

## Priority: 🟡 Medium

Public invitation adalah traffic utama.

Implementasikan Redis caching dengan hati-hati.

### Invitation Cache

Cache:

```text
public invitation data
```

Jangan cache data private.

### Cache Invalidation

Ketika invitation berubah:

```text
Update invitation
    ↓
Invalidate cache
```

Jangan menggunakan TTL sebagai satu-satunya mekanisme invalidation.

### Image Optimization

Saat upload:

* Validate image
* Resize jika diperlukan
* Compress
* Generate optimized format jika architecture mendukung
* Preserve original jika diperlukan

Jangan melakukan processing berat dalam synchronous HTTP request jika queue infrastructure sudah tersedia.

### Lazy Loading

Gallery:

* Lazy load images
* Responsive images
* Avoid loading full-resolution images immediately

# DEVELOPMENT RULES

## Architecture

Sebelum coding:

1. Audit existing architecture.
2. Cari service/repository/API/component yang sudah tersedia.
3. Reuse existing implementation.
4. Hindari duplicate logic.
5. Ikuti naming convention project.
6. Jangan membuat abstraction baru jika abstraction existing sudah cukup.

---

## Testing

Setiap phase harus memiliki test.

Minimal:

### Backend

* Unit test
* Feature/API test
* Authorization test
* Validation test
* Error handling test

### Frontend

* Build
* Lint
* Component test jika infrastructure tersedia
* Browser QA untuk critical flows

### Regression

Pastikan:

```text
Existing tests
        ↓
Still passing
```

Pre-existing failures harus tetap didokumentasikan.

# DEFINITION OF DONE

Sebuah feature hanya dianggap selesai jika:

* [ ] Implementation selesai
* [ ] Existing architecture dipatuhi
* [ ] Authorization aman
* [ ] Validation tersedia
* [ ] Error handling tersedia
* [ ] Test ditambahkan
* [ ] Existing test tidak regression
* [ ] Formatter/linter passed
* [ ] Build passed
* [ ] Critical flow diuji
* [ ] Tidak ada secret/API key yang hard-coded
* [ ] Tidak ada fake/mock implementation di production code
* [ ] Tidak ada TODO kritis yang sengaja ditinggalkan
* [ ] Evidence hasil test tersedia

## FINAL RULE

Jangan langsung mengubah banyak file tanpa audit.

Untuk setiap wave:

1. Audit.
2. Buat implementation plan.
3. Implementasikan.
4. Test.
5. Review perubahan.
6. Fix regression.
7. Jalankan final verification.
8. Commit perubahan secara terpisah dan jelas.
9. Laporkan file yang berubah, test result, dan known deviation.

**Prioritas pertama adalah Wave 1: Admin Dashboard + Email Notification.**
Jangan mulai Wave 2 sebelum Wave 1 selesai dan terverifikasi.
